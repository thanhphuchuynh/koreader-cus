KOReader performance check

26 October 2026 · Native Apple Silicon macOS preview · KOReader v2026.07.2-280-g400ba0e

The strongest measured lookup bottleneck is a 125 ms subprocess polling delay. Page rendering and popup creation are much quicker on this Mac. The custom popup also has a reproducible scrolling crash.

Later update: the missing scroll-dialog owner was corrected while adding optional AI help. These timings and crash evidence describe the build before that change; the new build has not been rebenchmarked.

Findings, in priority order

  1. Fix the popup scrolling crash first. Reproduced in all three current-build runs and absent from baseline/SimpleUI-only runs. englishpreview.koplugin/main.lua creates ScrollTextWidget without dialog. Scrolling calls updateScrollBar(true), which dereferences self.dialog.movable at native scrolltextwidget.lua:176. This is a stability defect in our customization, not evidence that Lua or KOReader is generally too slow.
  2. Investigate the lookup polling delay. Native ui/trapper.lua:393–416 schedules its first output-read check after 0.125 seconds. Exact lookups cluster around 128–129 ms in every configuration, while direct sdcv runs take about 7 ms. This explains most observed exact-lookup latency here. A future change must preserve cancellation, responsiveness and subprocess cleanup; lowering a global interval blindly is not validated.
  3. Avoid laying out long definitions twice. Our popup first constructs a full TextBoxWidget for measurement, then frees it and creates ScrollTextWidget when the result is tall. Current popup create+paint is about 13 ms versus 8 ms baseline. This is measurable overhead, but much smaller than the lookup wait on this Mac.
  4. SimpleUI is not the main lookup or page-turn bottleneck in this test. It adds approximately 0.12 seconds to median startup on the short fixture. Page-turn differences are small; startup samples are noisy. Neither the synthetic fixture nor this sample size establishes performance for large libraries or complicated books.

Method and limits

  • Disposable profiles under runtime/macos/performance/. Existing test settings, source application and book files were not edited by the probes. Dictionaries are shared read-only via a symlink.
  • Three launches per configuration, rotated order. Same existing settings and dictionary data; baseline means optional SimpleUI/English plugins and the dictionary overlay removed, not factory-default settings. No filesystem-cache purge; these are predominantly warm measurements.
  • Per configuration: 75 processed exact-lookup samples plus separate raw lookup calls, and 36 popup create/paint samples. Five words include four found entries and one deliberately missing word. Direct sdcv: 25 processes, with found-word median reported separately. These stages were timed independently; popup timing excludes lookup time.
  • Initial startup/dictionary tests use the short original sample EPUB. The initial no-op paging measurements from that fixture were discarded. Separate paging runs use a generated 44-page EPUB and 10 verified transitions per configuration between pages 1 and 2, including native repaint. Paging sample size is small and only those cached pages were exercised.
  • Startup ends after ReaderUI initialization; it is not a measurement of the first visible frame. Popup/page timing includes native repaint submission, not input latency, display scanout or E Ink completion.
  • Peak process RSS comes from macOS /usr/bin/time -l; it includes native libraries, fonts, dictionary maps and retina rendering. It must not be used as a Kindle RAM estimate. This is not a memory-leak, battery, CPU-idle or thermal study.
  • No Kindle hardware, fuzzy-search benchmark, PDFs, scanned pages, large-library browsing or online analysis was tested. No speed improvement or product fix is claimed. The installed customization remains unchanged.
